## Project Overview

Zyiarah is a Flutter-based service booking platform (cleaning services) targeting iOS and Android. It includes a React/TypeScript admin web panel and a Firebase Cloud Functions backend. The app supports three user roles: **client**, **driver**, and **admin** (sub-types: super_admin, orders_manager, accountant_admin, marketing_admin).

- **Bundle ID**: com.zyiarah.zyiarah (iOS App Store ID: 6760955777)
- **Version**: see `pubspec.yaml` (`version:` line — build number auto-increments in CI)
- **Firebase Project**: zyiarah-app

## Architecture

### Flutter App (`lib/`)

Entry point is `main.dart` (Firebase init + auth wrapper). Navigation is handled by `router.dart` using **GoRouter** with deep link support. State management uses **Provider** (`ChangeNotifierProvider`).

Key directories:
- `lib/models/` — data models (User, Order, Service)
- `lib/screens/` — client and driver screens
- `lib/screens/admin/` — admin-only screens (orders, drivers, zones + pricing, coupons, contracts, policies, analytics, e-invoice log, fleet radar, broadcast)
- `lib/utils/` — pure helpers shared by screens and tests (`day_capacity.dart`, `terrain_surcharge.dart`, `home_packages.dart`, `phone_format.dart`, …)
- `lib/services/` — all business logic and integrations (see below)
- `lib/providers/` — UserProvider, ConfigProvider, OrderProvider
- `lib/widgets/` — reusable UI components

`ZyiarahFirebaseService` (`lib/services/firebase_service.dart`) is a factory singleton — call it as `ZyiarahFirebaseService()`, **not** `.instance` (`_instance` is private; there is no `.instance` getter, so code written against one will not compile). Its scope is **auth and account provisioning**, not Firestore access: sign-up/sign-in **by real email only**, password reset, `signOut`, `getUserRole`, `saveUserToRegistry`, worker-photo upload, and `createAccountViaAdmin` / `createDriverAccountViaAdmin`. **There is no phone login and no OTP** — this file used to claim both, and the claim was false: the six methods behind them (`_phoneToEmail`, `signUpWithPhoneAndPassword`, `signInWithPhoneAndPassword`, `updatePassword`, `verifyPhoneNumber`, `verifyOTP`) had no caller anywhere and were deleted on 2026-10-04 (see *no dead members* below). Signup goes through `signUpWithRealEmailAndPassword` and the login screen's field is an email. If phone login is ever wanted, note what the dead code got wrong: `_phoneToEmail` stripped `966` and then a leading `0` **in that order**, so `00966…` became `0966…@zyiarah.com` and `0966…` became `966…@zyiarah.com` — one phone number, two different accounts, depending on how she typed it. The correct normaliser was sixty lines below it the whole time, inside `getUserRole`: `00966` explicitly, then `966`, then the leading zero, then the last nine digits.

It is **not** a Firestore gateway, and describing it as one misleads: 15 of 139 files under `lib/` import it, while 72 call `FirebaseFirestore.instance` directly and 57 of 69 screens import `cloud_firestore` themselves. Screens query Firestore directly by design here — so a cross-cutting concern (caching, retry, logging, App Check) has no single chokepoint to land in, and adding one means touching those 72 files. Weigh that before assuming a central hook exists. Firestore offline persistence is enabled with unlimited cache.

Two things about the guard matter more than the count. **It masks comments and strings before counting**, because a name that appears only in a comment is not a use — that is how `notifyUserOfSupportReply` and `notifyAdminOfPayment` hid, each named only in the comment explaining why its call was removed, and `notifyAdminOfPayment` even has a test asserting the screen does *not* call it. Masking must keep `${…}` interpolations intact, though: the first version blanked whole strings and declared `formatSar` dead while `hourly_details_screen` calls it three times inside `"${formatSar(x)} ر.س"`. And **the generic check matches names, so it is blind to a member whose name collides with a package API** — `user.updatePassword` (FirebaseAuth), `_auth.verifyPhoneNumber` (FirebaseAuth), `Moyasar.verifyOTP` (the payment package), and `httpsCallable('checkHourlySlotAvailability')` (the Cloud Function the dead Dart wrapper of the same name called) all read as uses. That is exactly how half the phone surface stayed invisible, so the generic check is followed by **explicit blocklists** in the style of `no_tabby_test`. A bite test proves the split is real: reintroduce `verifyOTP` and the generic check stays **green** while only the blocklist fails. One loose end this left server-side: `exports.checkHourlySlotAvailability` in `index.js` now has **no client at all** (the screens call `getHourlyAvailability` directly via `httpsCallable`), but deleting a Cloud Function is a human decision run by hand — the deploy carries no `--force` and would fail instead of silently removing it.

### Admin Web Panel (`admin_panel/`)

React 19 + TypeScript (Vite), Tailwind CSS, MapBox GL for map views. Connects to the same Firebase backend. Deployed to Firebase Hosting under the `admin` target.

**Routes are code-split and must stay that way.** Every page except `Dashboard` and `Login` is a `lazy(() => import(...))` in `App.tsx`; those two stay static because one is the landing page after login and the other is what an unauthenticated visitor sees first, so deferring them adds a round trip before anything renders. This matters because `mapbox-gl` — by far the heaviest dependency — is imported by exactly one file, `Settings.tsx`: before splitting, every admin downloaded the whole map engine to see any screen. First load went from 860 kB gzipped (3,025 kB JS + 140 kB CSS) to **287 kB** (906 kB JS + 91 kB CSS), with Mapbox and its stylesheet now in a `Settings` chunk fetched only when Settings opens — and `/settings` is denied to `accountant_admin` and `marketing_admin`, so those roles never fetch it at all. The `Suspense` boundary sits **inside** `guard()`, after the `canAccess` check, for two reasons: a single boundary around `<Routes>` would blank the sidebar and header on every navigation, and putting it after the role check means a denied page returns `<Navigate>` without ever rendering the lazy element, so its chunk is never requested — **the role gate is also a download gate**. Reverting one `lazy` to a static import is a completely silent regression: nothing in the UI changes, no other test fails, and the cost shows up only in build output nobody reads (one page costs ~28 kB). `src/App.split.test.ts` is that reader.

**The map is now its own chunk too (2026-10-03), and that closed the smaller hole route-splitting left.** Route-splitting put `mapbox-gl` in the `Settings` chunk, which was a real win, but opening Settings on *any* tab — payments, force-update, daily cap — still fetched the whole map engine even if the coverage tab was never opened. All of it moved into `src/components/ZoneMapPicker.tsx`, `lazy()`-imported by `Settings.tsx` and rendered only inside `{showAddForm && (`, so Mapbox arrives when an admin opens the add-zone form and not before. Measured with `npm run build`: the `Settings` chunk went from **1,917.68 kB (530.74 kB gzipped) to 75.72 kB (20.16 kB)**, with a new `ZoneMapPicker` chunk at 1,842.81 kB (511.16 kB) plus the 48.82 kB of Mapbox CSS that moved with it; the main bundle also shed ~3 kB gzipped. The surface was smaller than it looked — 11 `mapboxgl` references, not ~150 lines of entanglement — and `Settings.tsx` dropped to 1,475 lines. Two things make the split real rather than cosmetic, and both are guarded in `src/components/ZoneMapPicker.split.test.ts` (7 checks): **`lazy()` alone is not enough** — a deferred component mounted alongside the page is fetched immediately, so the guard asserts the picker's use site comes *after* the `showAddForm` gate and sits inside a `Suspense` boundary that actually encloses it (checking the last `<Suspense` before the use site against the last `</Suspense>`, not a distance regex); and **`src/utils/mapboxArabic.ts` is the second half of the separation** — it imports `mapboxgl` at module scope *and registers the RTL plugin as a side effect*, so leaving its import in `Settings.tsx` would keep the dependency in that chunk even with the direct `mapbox-gl` import gone. The guard therefore pins that exactly two files import `mapbox-gl` (the picker and the arabizer) and that only the picker imports the arabizer. `circleGeoJSON` moved to `src/utils/` rather than into the picker: it is pure geometry with no Mapbox dependency, and exporting a function from a component file breaks React fast-refresh. The picker takes `onPick`/`onReject` callbacks instead of reading `notificationContext`, so it tests without providers. Enumerate source files with `import.meta.glob`, not `node:fs` — the latter has no types under `tsconfig.app.json` and has now tripped two guards here.

### Firebase Backend (`functions/index.js`)

Node.js v22 Cloud Functions — **63 exported functions in one 6,168-line `index.js`** (21 `onCall`, 17 `onDocumentUpdated`, 9 `onDocumentCreated`, 8 `onSchedule`, 4 `onDocumentWritten`, 3 `onRequest`, 1 `onTaskDispatched`). Ten logic modules are extracted — `pricing.js`, `capacity.js`, `notify_prefs.js`, `vat.js`, `drivers.js`, `amounts.js`, `slots.js`, `moyasar_api.js`, `tamara_api.js`, `refund_engine.js` (the other root `.js` files are standalone diagnostics and eslint config) — so expect every backend change to touch `index.js` and to conflict there. Seven are fully pure; `moyasar_api.js` and `tamara_api.js` own the HTTP transport to the payment gateways (`fetch`), tested with a stubbed global `fetch`, never the network.

**The "no module touches Firestore" rule is gone, replaced by a sharper one (owner decision, 2026-10-03).** `refund_engine.js` reads, writes and runs transactions. What mattered about the old rule was never purity for its own sake — it was that a module can be tested without an emulator. So the rule that replaces it is the one that actually protects that: **a module never calls `getFirestore()`, `getApp()` or `initializeApp()`; it receives `db` as its first argument**, and anything else that writes (here `queuePush`) is injected too. `refund_engine.test.js` runs 28 checks against a ~40-line fake `db` — no emulator, no network — and its `(و٥)` check scans every module for those three calls. That check has to strip comments before scanning, because the module states the rule by naming `getFirestore()` in its own header and the first version failed on its own documentation; it then asserts the name *is* still present in the unstripped text, so over-stripping cannot leave the guard with nothing to find. `FieldValue` is imported directly and is not an exception: its sentinels (`delete`/`serverTimestamp`/`increment`) are built without an initialized app, which is why the fake-`db` tests can compare against `FieldValue.increment(230)` by value.

**Decomposing `index.js` is tractable, and the map is what makes it so.** 36 test files read `index.js` as text (23 Dart guards, 13 functions-side, one of which — `payWithWallet.test.js` — actually `require`s it, so the file must stay loadable with all 62 exports). That sounds prohibitive, but of the 110 symbols defined in `index.js` only **53 are named by any guard** — the other 57 are cold and move without touching a single test. (Re-derive the numbers each time; they drift as slices land, and the figure is only comparable if you use the same definition of "symbol": top-level `function`, `const NAME =`, and `exports.NAME =`.) Derive that map before planning a slice (grep each defined symbol against the guard corpus) rather than guessing: the cold set clusters cleanly by concern (Moyasar low-level, Tamara/Tabby, refunds, contracts/visits, email/HTML). And extract by **concern, one slice per PR** — each slice's real payoff is usually the duplication it reveals, not the line count. The Moyasar slice moved only 60 lines out of `index.js` yet collapsed four separate hand-written copies of the auth header and three of `GET /payments/{id}`, and fixed a live bug (see Payments below). Each slice should end with a guard forbidding direct access outside its module, or the duplication simply regrows — it had regrown four times before the Moyasar slice and nine times before the Tamara one. Five slices in: Moyasar (60 lines, a live void/capture bug), Tamara/Tabby (an approved order skipped silently), amounts (a latent sweep refusal), refunds (191 lines, **a live silent burial**), slots (23 duplications, a latent "driver reads as free"). The payoff is not always a defect, and saying so matters: the slots slice found **no divergence at all** — seven conflict scans, all −24h, all the same status set, all the same comparison — so it is openly preventive, and its own test says that in its header rather than dressing it up. Two slices also left stale comments behind in `index.js` describing code that had moved; grep for orphaned headers after each one.

Two warnings from doing the first two slices. **The symbol map has a blind spot: it maps names, not string literals.** A guard can pin a URL or a request-body shape without naming any function, so `grep` the moved *literals* against the guard corpus too — that is how `notification_dedup.test.js` turned out to pin Tamara's refund URL and amount shape while naming none of the moved symbols. And **a guard that strips `//` comments naively cannot see a URL**, because `https://` contains `//`: the first version of the Tamara guard was inert for exactly that reason and its bite test is what exposed it. Strip whole-comment lines instead, and only trailing `//` not preceded by `:`. `moyasar_api.test.js` deliberately does not strip at all (stricter, no false negative possible) because `index.js` has no comment naming that URL, while it has two naming Tamara's and Tabby's — so the two guards differ on purpose and should not be unified. Handling:
- FCM push notifications (Firestore triggers: orders, tickets, contracts, dispatch)
- Email via Resend (through the `notification_triggers` queue — anti-relay guarded)
- Payment webhooks & operations: Moyasar (primary; webhook + verify/refund/void/capture), Tamara — all HMAC-verified and idempotent; a Tabby webhook/refund pair is kept only for orders paid before Tabby was removed from the app (2026-09-30)
- Wallet operations (`payWithWallet`, `redeemQatratPoints`, `onOrderRewards`) — all wallet writes are server-side only
- Direct Dispatch engine (driver assignment, slot availability, surge pricing)
- Account deletion processing (Apple requirement)

All callable functions require authentication; sensitive ones also verify ownership or admin role (`_assertAdmin`). Secrets are managed via `defineSecret` / Secret Manager — never hardcode keys.

Skipping deletes`. **No `--force`, deliberately:** with `--non-interactive` alone the deploy *fails* when a function has disappeared from the source, instead of deleting it from production in silence — removing a function is a human decision, run by hand once. `test/functions_deploy_guard_test.dart` pins that, plus tests-before-deploy (the workflow re-runs them itself, because `workflow_dispatch` can fire on a state no PR guarded), `--only functions`, the explicit `--project`, `cancel-in-progress: false` (cancelling mid-deploy leaves the functions half-published) and Node 22 in lockstep with `functions/package.json`'s engine. **The admin panel deploys automatically too (2026-10-04)** — `.github/workflows/admin_deploy.yml`, on a push to `main` touching `admin_panel/**`, `firebase.json`, `.firebaserc` or `lib/firebase_options.dart`: lint, tests and **build** all before `firebase deploy --only hosting:admin` (build after deploy would publish the previous `dist`). It was the same hole as the functions: the map-chunk split of 2026-10-03 was merged and never seen by an admin. The new wrinkle is that `admin_panel/src/services/firebase.ts` is **gitignored**, so every build path had to manufacture it — `ci.yml` carried a hand-written placeholder that type-checks but cannot be deployed and drifts from the real file in silence. Both paths now call one generator, `admin_panel/scripts/gen_firebase_config.mjs`, which reads the `web` block of **`lib/firebase_options.dart`** — already committed, already used by the Flutter web build, and not secret: a Firebase web config ships inside the bundle and any visitor can read it; the protection is Firestore rules, not hiding the key. The generator anchors on `FirebaseOptions web = FirebaseOptions(` specifically, because Android and iOS repeat the same field names with different values in that same file and a loose match yields another platform's key and a panel that cannot sign in. A missing `MAPBOX_TOKEN` **fails the job**: it would not break the build, it would leave `mapboxgl.accessToken` empty so the zone map silently cannot draw in production. `test/admin_deploy_guard_test.dart` pins all of it — the target (`hosting:admin` only, so the landing page is never republished from here), the order, `cancel-in-progress: false`, the key cleanup, that **neither** workflow contains an inline `initializeApp(`, and that the generator still exports every name the panel imports (`auth`, `db`, `storage`, `functions`, default) — a check `tsc` independently enforced when a bite test dropped `storage` and the build failed with TS2614.

Any `AuthKey_*.p8` file at root is an App Store Connect API key — gitignored; never commit or expose it. Add `[skip ci]` to commit messages that shouldn't trigger a build (docs, rules-only changes) — note this skips **both** Codemagic builds (iOS and Android) **and all five GitHub Actions CI jobs**, because Actions honours the same marker natively. A PR whose head commit carries it shows *zero* checks, not green ones. So don't put it on a PR commit you still want guarded: leave the PR commits clean and put the marker in the **squash-merge message** instead — that skips the release build while the PR's own checks still ran.

The match is purely textual and has no notion of quoting or intent: a commit message that merely *mentions* the bracketed marker — documenting it, or quoting it in a subject line — is skipped exactly like one that means it. (This paragraph exists because the commit that first documented the behaviour was silenced by the marker in its own title.) To write about it in a commit message, drop the brackets: bare `skip ci` matches nothing. The full set Actions recognises is `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]` — all bracketed, all case-insensitive.

The Android workflow (`android-release`) mirrors iOS: it declares the same push-to-`main` trigger, builds a signed AAB **and** a tester APK with the same `versionCode`, and publishes to **two** places. ## Important Patterns

- **Auth service**: reach auth and account provisioning through `ZyiarahFirebaseService()` — the factory call, never `.instance` (it does not exist). Firestore reads/writes are made directly from screens via `FirebaseFirestore.instance`; there is no service layer in front of them (see the note under *Flutter App* above)
- **Role checks**: User role is stored in Firestore and accessed via `UserProvider`; always verify role before rendering admin-only UI
- **Arabic support**: plain `Text()` is **correct** for Arabic in the UI — Flutter shapes and bidi-orders Arabic natively, and there are ~528 such literals across `lib/`. Do **not** pass UI strings through `arabic_reshaper`: pre-shaping text Flutter will shape again garbles it. `arabic_reshaper` is needed in exactly one place — `zyiarah_pdf_service.dart`, because the `pdf` package draws glyphs without shaping them; that file wraps it in a single static helper `_ar()`, so every Arabic string in a PDF goes through that one call. `bidi` is declared in `pubspec.yaml` but imported nowhere in our code (the `pdf` package pulls it in itself)
- **`google_fonts` may only be asked for what the bundle ships — `test/font_assets_guard_test.dart`.** `main.dart` sets `GoogleFonts.config.allowRuntimeFetching = false` on purpose (a first run without internet rendered a garbled fallback across the whole UI), so a family or weight that is not in `pubspec.yaml` **fails**: the package throws, catches its own exception, and returns a style with **no fontFamily** — the text renders in the system font instead of Tajawal. No crash, no failing test, nothing in `analyze`. **Found by running the app** (2026-10-04, Flutter web in headless Chromium): the splash alone logged **376 `Roboto-Bold` exceptions in 28 seconds** — one per animation frame — plus one for `Tajawal-ExtraBold`. A full scan then found **45 weight sites** and **two unbundled families**: `GoogleFonts.roboto` on the splash wordmark and `GoogleFonts.ibmPlexMono` on the order code in `order_success_screen`. Only Tajawal ships, at 400/500/700/900. The fix snaps each request to the nearest bundled weight, heavier on a tie (600→700, 800→900), and both families to Tajawal — note **Tajawal has no 600 upstream at all**, so no asset could ever satisfy it and changing the request was the only option. Verified the same way it was found: console lines 1527 → 20, font exceptions 377 → 0. The guard reads the weights **from `pubspec.yaml`** rather than hard-coding them, matches each `GoogleFonts.x(` call by balanced parens (a plain `TextStyle` weight is fine — the engine picks the nearest bundled weight silently; only the *package* lookup fails), and masks comments by **overwriting them with spaces** so offsets stay aligned: the first attempt at this fix deleted comment lines instead, shifted every offset, and rewrote four call sites in the wrong places. It also pins that runtime fetching is still off, since that is what makes the rest strict. There is deliberately **no** check that the declared font files exist: it was written, found inert — the Flutter tool fails first with «unable to locate asset entry in pubspec.yaml» — and removed, because a check that cannot bite is worse than none
- **PDF generation**: Use existing service classes in `lib/services/`; they depend on the `pdf` and `printing` packages
- **Payments**: Moyasar is primary (cards, STC Pay, Apple Pay); Tamara handles installments — Tabby was removed at the root on 2026-09-30 (owner uses Tamara only; `test/no_tabby_test.dart` guards it, and legacy Tabby orders stay displayable and refundable); wallet is supported. Cash on delivery was removed at the root by owner decision — `test/no_cod_test.dart` guards it; never reintroduce it. All paid orders get a ZATCA invoice
- **All Moyasar HTTP goes through `functions/moyasar_api.js`** — `authHeader`, `getPayment`, `listPayments`, `refund`, `voidPayment`, `capture`. It had been written by hand in seven places: the auth header built from scratch in **four**, `GET /payments/{id}` in **three**, and `POST /refund` and `/void` in **two** each. The copies were not equivalent, and that was the real defect: `_moyasarRefundCore` parsed the response with `.catch(() => ({}))`, the inline refund wrapped `fetch` + parse in a `try`, and the inline **void and capture called `await response.json()` bare** — so a non-JSON body from a proxy in front of Moyasar threw a raw parse error and the intended Arabic message (`result.message ?? "فشل إلغاء عملية الدفع"`) never reached the client. The module parses tolerantly, so `result` becomes `{}` and `ok` is false and the caller throws what it meant to. What is deliberately **not** unified is the error contract: the module **never throws on an HTTP status**, it returns `{ok, httpStatus, status, result}`. An `onCall` needs to throw `HttpsError` so the client sees a message; the automated paths (the sweep, the auto-refund) need a status so they can decide. Two contracts over one transport. Network errors propagate, except in `getPayment`, which swallows them on purpose: every caller asks it *before* deciding to void or refund, and "couldn't ask" must read as "don't know" so the conservative path is taken, not as a reason to abort. The policy that decides *whether* to void or refund is not here — it is in `refund_engine.js` (it takes `db`); this module only carries the call. `functions/test/moyasar_api.test.js` stubs the global `fetch` (never the network) and its last check is the one that matters: **no `api.moyasar.com` URL and no hand-built auth header anywhere outside the module**, because without that the seventh inline call appears in the next feature and nothing fails
- **All Tamara and Tabby HTTP goes through `functions/tamara_api.js`** — `checkout`, `getOrderByReference`, `authorise`, `refund`, and `tabbyRefund`. The `Bearer` header was hand-built in **nine** places (in two different spellings), `GET /merchants/orders/reference-id/{id}` written **three** times and `POST /orders/{id}/authorise` **three**. All three copies of the reference lookup parsed the response with a bare `await r.json()`, and the consequence differed by site — the worst being silent: inside the two sweeps the parse error is caught per-document, so an order **Tamara had already approved** is skipped and never confirmed, with nothing written anywhere saying why; in the refund path it logs "lookup" so it looks as though Tamara does not know the order. Tolerant parsing in the module fixes all three. Amount units differ per gateway and must not be crossed: Moyasar takes **halalas**, Tamara a **riyal number** inside `total_amount`, Tabby a **string with two decimals**. The module's tests pin each. Tabby's surface is deliberately **refund-only** (owner decision, 2026-09-30): `tabbyWebhook` and `tabbyRefundPayment` were kept because orders paid through Tabby may still exist with ZATCA invoices issued, so deleting the refund would leave a customer with no recourse. `test/no_tabby_test.dart` guards the *client* side (package, service, key, boot, selection) and reads only `lib/`; `tamara_api.test.js` guards the *server* side — exactly one Tabby operation and one Tabby path — so adding a Tabby checkout would make it a payment gateway again through the back door
- **The auto-refund engine is `functions/refund_engine.js`, and it alerts its own failures** — `reopenFieldsIfSystemCancelled`, `reconcileAndSettle`, `voidOrRefundTampered` (price tampering, Tier B), `autoResolveUnfulfilledPaidOrder` (#18: a paid order whose window closed with no driver), `notifyAutoRefund`, `escalateFailedAutoRefund`. One concern: *a paid order that cannot be fulfilled gets voided or refunded, exactly once, and the client is told.* **The slice revealed a live defect, and it is the reason the module exists rather than just tidier code.** `autoResolveUnfulfilledPaidOrder` has four failure branches (`no_payment_id`, `gateway_error`, `wallet_error`, `no_amount`); each wrote `stranded_alerted: true` and **none of them sent anything** — `queuePush` appeared nowhere in the function except on its two success paths. The sweep then read `if (["gateway_error","wallet_error","no_amount","no_payment_id"].includes(r.reason)) continue;` with the comment "المعالج ضبط stranded_alerted؛ لا نُكرّر التنبيه" — skipping its own alert on the strength of an alert that was never sent. And the flag was usually already `true` anyway: the **early-warning** branch higher in the same sweep sets it hours earlier to mean something different ("passed its start time, still trying"), so the fall-through `if (d.stranded_alerted === true) continue;` would have skipped too. With `auto_refund_processed` never released, no later sweep retried. Net: **money collected, service never delivered, refund failed, nobody told, no second attempt** — precisely the hole `stranded_alerted` was added to close (`test/driver_audit_fixes_test.dart` still records it: "طلب مدفوع فات موعده بلا سائق كان يختفي خادميّاً بلا تنبيه"), reopened from another path by the auto-refund feature itself. That guard passed throughout, because it checks that the *string* appears in the sweep, not that an alert is sent. The fix is one escalation push per failure, from the engine (the only thing that knows the refund failed), on a **separate** flag `auto_refund_alerted` so the early-warning flag cannot mute it, targeted at `super_admin`/`orders_manager`/`accountant_admin`. Two guards keep it from regrowing: `auto_refund_failed: true` may appear **exactly once** in the module — inside the one helper that also escalates, so a branch cannot pin the failure silently — and the sweep's reason list must stay **set-equal** to the module's `ESCALATED_REASONS`, since a reason in the sweep's list that the engine does not escalate is a silent burial again, while one it escalates that is missing from the list is a double alert. `reconcileAndSettle` collapses the other half: "ask the gateway, finish if it already refunded, otherwise `void` an uncaptured authorization and `refund` a captured one" was written twice in two different shapes, and `index.js` must now contain neither `"authorized"` nor `"initiated"` — that guard reads the raw source without stripping comments, like `moyasar_api.test.js` and unlike `tamara_api.test.js`, because no comment in `index.js` names those states. **`payment_status: "refunding"` is now transient, and the "read nowhere" note was wrong (2026-10-04).** It *is* read: `admin_order_details_screen` builds its Moyasar operations card from `moyasar_status ?? payment_status`, and a wallet- or Tamara-paid order carries no `moyasar_status` at all. Stuck on `"refunding"`, every one of `canVoid`/`canRefund`/`canCapture` **and** `alreadyFinal` goes false, so the card renders an empty `Wrap`: a title, a payment id, a badge printing `refunding` in Latin script inside an Arabic UI — and then no button and no reason, at exactly the moment a failed auto-refund has escalated to that admin. Two of the four failure branches left it set. `wallet_error` now resets to `"paid"` (the wallet transaction is atomic: either it all committed or nothing moved, so "refund in progress" was simply false), and `gateway_error` becomes `"payment_review"` — this module's own word for the same case in `voidOrRefundTampered`, and one `index.js` already knows in two places so it will not auto-revive the order (both are gated on `is_paid !== true`, so neither is reached here anyway). Every exit from the function now replaces the marker. Four checks in `refund_engine.test.js` pin it: exactly two write sites, no failure branch without a `payment_status`, the used states set-equal to `{paid, payment_review}`, and — after stripping comments, since the module documents the decision by naming the word — that the word is still in the raw text. `test/admin_payment_ops_card_test.dart` (11 checks) pins the card: a branch that explains itself when no operation applies, distinguishing "no gateway payment at all" from "no operation on state X", and ordered **after** `alreadyFinal` so it cannot swallow a settled payment.
- **"Which field is the amount?" has two named answers, in `functions/amounts.js`** — `expectedAmount(data, amountField?)` asks *how much should have been paid* (the anti-tamper check before confirming a paid order) and `refundAmount(data)` asks *how much do we refund*. Both resolve `final_amount ?? total_amount ?? planPrice ?? amount`, and `final_amount` must come first because it is the admin-approved price, shown against the cart total in the store-orders screen as "المعتمد: X (السلة: Y)" — comparing against the stale base, as `moyasarWebhook`'s own comment says, "rejects a genuine payment when the price is adjusted". The two are separated by name although they agree today, because they are not the same question: one is compared against what the gateway sent, the other is sent to it. The chain had been hand-written at six sites and one disagreed: `reconcileOrphanPayments` put `amount` first. Because its comparison is `paidH >= expectedH` (not equality) the effect is one-directional — an **upward** adjustment still recovers, but a **downward** one (an item removed, a goodwill discount) makes expected exceed paid, so the sweep logs "amount too low" and refuses to recover an order the client has already paid for, which is the one thing that sweep exists to do. **It is latent, not live, and the distinction is part of reporting it honestly:** nothing in the repository writes `final_amount` (12 reads in `index.js`, zero writes), and a store order is created with `amount == total_amount`, so every site resolves to the same value today. It becomes live the moment `final_amount` is set out of band — which the code's own comments anticipate ("بعد تعديل الإدارة") and the admin screen already displays. The fix is preventive. `??` not `||` throughout, because an explicit `0` is a decision (a free order, a full settlement), and `||` would skip it and bill a customer an amount they do not owe. **Display amounts deliberately do not go through this module** — an email total line and a notification row answer "what do we show", use `||` so a zero falls through to another field, and that is fine where no money is compared; `amounts.test.js` allowlists exactly those two chains by comparing the whole set, so a seventh inline chain fails the guard
- **Pricing is server-verified**: the client shows prices, but `functions/pricing.js` recomputes the base from the zone document (per-service rates, optional `terrain_surcharge_percent`) on every Moyasar/wallet payment and flags underpayment. `PriceBreakdown` (`lib/utils/terrain_surcharge.dart`) is the single client formula: base + terrain + surge − discount = net, + 15% VAT = total; fixed-price contracts skip all three
- **VAT has one source, and two models**: the rate lives in `lib/utils/vat.dart` (`kVatRate`) and `functions/vat.js` (`VAT_RATE`) — never write `1.15` or `0.15` again (it was hand-written in 27 places across 18 files; Saudi VAT really did change, 5%→15% in 2020, and a missed site produces wrong invoices *silently*). Two models coexist and both are correct in place, so the helper names carry the model: **added on top of a base** → `vatOnBase` / `grossFromBase` / `grossFromBaseRounded`; **extracted from a VAT-inclusive gross** → `netFromGross` / `vatInGross`. The names matter because the same word means both: `store_schedule_screen.total` is a *base* (VAT added on top) while `store_payment_screen.total` is a *gross* (VAT extracted) — the first passes `_grandTotal` to the second. The helpers deliberately do **not** round, because call sites differ (`grossFromBaseRounded` is the one exception, matching the charged-amount convention). `test/vat_test.dart` and `functions/test/vat.test.js` are property tests: each helper is checked against the old hand-written literal across the full price range, because `1 + 0.15` and `1.15` are bit-identical doubles and the refactor must not shift a cent — the server compares paid vs expected with a `> 0.01` tolerance, so a last-bit drift at the boundary would reject a valid payment or accept a short one
- **"How long does this order hold a driver, and does it overlap?" lives once, in `functions/slots.js`** — `ORDER_HOURS_DEFAULT`, `CONFLICT_LOOKBACK_HOURS`, `CONFLICT_STATUSES`, `orderHours(data, override?)`, `orderEnd`, `conflictWindowStart`, `overlapsSlot`. Pure, no `db`. The duration chain `Number(x.hours_contracted || 4)` was hand-written **16** times and the conflict scan (−24h window + active-status set + the overlap comparison) **7** times, across 10 functions. **There was no divergence, and the slice says so rather than dressing it up:** all seven windows were −24h, all the status sets equal as sets (two spellings, same members — irrelevant to an `in` query), the comparison `slotStart < orderEnd && orderStart < slotEnd` identical in all five, the default 4 in all sixteen. So this one is openly **preventive**: changing the default — a plausible product decision — today means editing 16 sites together, which is the VAT story's exact shape (27 sites, 5%→15%, one missed site billing wrong silently). What it *did* fix is latent and about one paren: `Number(x || 4)` yields `NaN` for a corrupt or non-numeric value, `new Date(start + NaN)` is an `Invalid Date`, and **every comparison against an Invalid Date is false — which reads as "the driver is free"**, so a corrupt field silently double-books. `Number(x) || 4` falls to the conservative default instead; nothing in the repo writes a non-numeric or negative `hours_contracted`, so it is latent, not live. Note `||` is **correct here and wrong in `amounts.js`**, and the two bullets disagree on purpose: an explicit `0` riyals is a decision, an explicit `0` hours is an unset field. The override argument also uses `||` deliberately, matching `durationHours || orderData.hours_contracted || 4` exactly — a test caught the first version treating a `0` override as present, which would have silently halved a direct-dispatch window. **Not unified, by owner decision:** `unassignJobsOnDriverDisable` queries `["scheduled", "assigned", "accepted"]` only, because "الجارية فعلاً (on_the_way/in_progress) تُترك عمداً — قرارها بشري", and `functions/test/slots.test.js` pins that it stays separate *and* that its comment survives. Two other five-element sets remain inline because they answer different questions (notify-the-client-of-a-reschedule, ops-health reporting); the guard compares the **whole set** of remaining literals, as `amounts.test.js` does, so a sixth inline set fails and gets reviewed deliberately. `pending` is excluded from `CONFLICT_STATUSES` by design — an unassigned order holds nobody — which is also why a reopened `pending` order still carrying a `driver_id` can have its date moved through the unguarded path harmlessly: it occupies that driver in no conflict query at all.
- **«تتبع السائق» واكتمالُ قاعدةٍ عولجت مرّتين.** The first fix moved the guard from the press into the button's visibility and wrote it as a rule instead of a two-status enumeration — both right — but the rule itself was written short: «a driver and a location». The same four July subscription visits came back in a later run the same day still showing «تتبع السائق», because they *do* have a driver and a location, with «انتهى الموعد» printed on the card right above the button. And **the first fix's own test pinned the shortfall**: "any status with a driver and a location is trackable" passes green over exactly that defect. The rule is now driver **and** location **and** the appointment has not passed — unless the order is under way right now (`on_the_way`/`in_progress`), because `appointmentPassed` works at day precision and a job starting at 23:00 reads as "passed" after midnight while the crew is still working; without that exception the fix would hide the map from a driver genuinely en route. `passed` is a **required** named argument, not a defaulted one, so a forgotten call site cannot keep the old behaviour silently — which is the exact shape of the shortfall being repaired.

- **The 30-day date strip auto-advances, so it must also scroll — `lib/utils/date_strip.dart`.** The three booking screens (`hourly_details_screen`, `subscription_plans_screen`, `event_worker_packages_screen`) each render an identical horizontal strip (`itemCount: 30`, chips `width: 58` + `margin: horizontal 5` = **68 px** extent, first chip is *tomorrow* — no same-day booking) and each **moves `_selectedDate` on its own** when the selected day is closed, full, or loses its driver to a longer package. None of them had a `ScrollController`, so the strip stayed at offset 0 while the selection could land on index 29. **This was live and a tester photographed it:** a zone schedule open on Saturday only pushed the selection to index 5, and on a ~360 px viewport (5.3 chips) the client saw Mon–Fri greyed out with the selected chip clipped at the screen edge — a row of days they cannot book, no visible selection, and the summary below naming a date they cannot see. `dateStripOffsetFor` centres the chip and `dateStripIndexOf` maps a date to its index; both are pure, and the offset is **logical, not visual** — 0 is the first chip, which is the *right* edge under RTL, so one formula serves both directions. `maxOffset` comes from `position.maxScrollExtent`, not from `30 * 68 - width`: the real layout bounds the scroll, and the guard pins that it is not replaced by a literal. `test/date_strip_test.dart` (30 checks) tests the arithmetic as a **property** — every index against 15 viewport widths, the chip fully inside the viewport — because the hole was in one corner and examples pass over corners; it then repeats the same property on a **real RTL layout** in a widget test, and pins the wiring per screen (controller attached to *that* `ListView`, `dispose`, and `_revealSelectedDate` called **once per auto-advance site** — 2 in `hourly_details`, 1 in the others — since an advance without a reveal is the original defect). It also pins the 58/5 geometry in all three screens against `kDateStripItemExtent`, so changing a chip's width in one screen cannot make the centring silently wrong. Trap found writing the widget test: **`MaterialApp` installs its own `Directionality` from its locale**, so a `Directionality.rtl` placed *above* `MaterialApp` is overridden and the strip lays out LTR — the harness must put RTL *inside*, which is also the real screens' order (each wraps its own subtree)
- **An empty list is not one state — `homePackagesView` in `lib/utils/home_packages.dart`.** `hourly_details_screen` printed «لا توجد باقات مسعّرة **في منطقتك** حالياً» whenever nothing was sellable, including when **no zone had been resolved at all** (`_selectedZoneName == null`, `_packages = []` — the out-of-coverage branch). So one screen said «موقعك الحالي خارج نطاق خدماتنا» in the location card and «your area has no priced packages» directly below it: a claim about an area the client does not have, which reads as *we serve you but have no price* and stops her, when the step she actually needs is to pick a point inside coverage. **The tester's screenshot showed both lines at once.** The decision is now a pure three-way state (`packages` / `noZone` / `zoneWithoutPackages`) so it tests without Firebase, and the per-area claim **names its zone** — a message that cannot be rendered without one. Note the precedence: a sellable option shows **even when the zone name has not arrived**, because a price is never withheld for a missing label. The sibling screens' «لا توجد باقات متاحة حالياً» is left alone: `subscription_packages` is a global collection, so that text claims nothing about an area. `test/home_packages_test.dart` pins the three states, that a blank or whitespace name is *not* a zone, and that the screen still calls the helper
- **The day strip's colours are computed against a duration, and before a package is chosen there isn't one — `homeStripDurationHours`.** `_firstFeasibleStart` scanned for a free window of `_durationHours`, the *field*, which is `4` at first and keeps the **previous zone's** value after `_applyZonePackages` clears a selection whose type is disabled in the new zone (it resets `type`, `crews` and price, not the duration). A longer stale duration narrows: a day with, say, 6 free hours renders **«محجوز بالكامل» in red** and its tap shows that message, although every package the client can actually buy there fits — a false claim that blocks a real booking, with no way for her to discover it. The rule is now: a selected package → its own duration; **no selection → the shortest *sellable* duration in the zone**, so a day is excluded only if it is too tight for every package she could buy; no sellable package at all → the default. The opposite direction was already handled and still is — picking a longer package auto-advances off a day that no longer fits (and now scrolls to it). `_durationHours` is untouched and still what the order carries: it is only read once a package is selected, which `_handleInitiateFlow` enforces, so the money path is unchanged — `test/home_packages_test.dart` pins both halves (derived for colouring, the field for the payload). Note this broke `zone_schedule_test`'s «خانات البدء محصورة بساعات الفتح» check, which pinned the literal `open[1] - _durationHours` as a **proxy** for the real decision (the anchor never exceeds close − duration). The decision is intact, so the guard was repointed and made *stricter*: it now pins the derived source and additionally forbids a hard-coded number in that bound
- **Capacity**: drivers have no zones; capacity is one global daily cap plus the **assignable**-driver count (see the next bullet — not merely the active count), optionally tightened by a zone's `max_orders_per_day`. Every consumer of `getHourlyAvailability` decides day fullness through `dayIsFull` (`lib/utils/day_capacity.dart`). Home cleaning is day-only (no arrival slot for the client)

Plain `npm audit fix` is fine and was applied. `functions/test/audit_posture.test.js` pins all of it: the production-resolved grpc-js version, that the package is not downgraded, that it stays in devDependencies, and that our code never imports uuid directly (which would make the advisory reachable)
- **`google_fonts` is pinned to major 8 on purpose, and `go_router` is on 18** — both 9.0.0 and 18.0.0 "migrate to `material_ui` and `cupertino_ui`", the Material/Cupertino libraries being extracted from the SDK into standalone packages. **Flutter 3.47.2 has not finished that move**: `flutter/material.dart` still defines its own `TextTheme` in `src/material/text_theme.dart` (862 lines, a full class) and does not re-export `material_ui`, so one name now has two classes. `google_fonts` 9 is written entirely against the package one, verified against the analyzer rather than inferred: `mui.TextTheme a = GoogleFonts.tajawalTextTheme()` passes while `TextTheme b = ...` fails, and `tajawalTextTheme(const mui.TextTheme())` passes while `tajawalTextTheme(const TextTheme())` fails. **The wall is on the return, not the argument** — building the base as `mui.TextTheme` compiles, then assigning the result to `ThemeData.textTheme` does not, so nothing short of a hand-written 15-field converter gets through. And there is nothing to gain: 9.0.0 is the migration, a higher SDK floor, `GoogleFontsLite` tree-shaking, and a long list of **added fonts** — while we use exactly one font (Tajawal) **already bundled as a local asset**, which `google_fonts` finds in `AssetManifest` before any network fetch. Note 9.0.0 declares `flutter: ">=3.47.0"` and we run 3.47.2, so `pub get` resolves it happily: the constraint does not protect you here, which is the recurring lesson that **`pub get` checks constraints, not classes**. `go_router` 18.0.2 by contrast is a clean upgrade with **zero code changes** — our surface is `GoRoute`/`context.go`/`push`/`pop`/`redirect`/`GoRouterState` and no `ShellRoute` at all, and 18.0.2's two fixes are `ShellRoute`-specific so they do not reach us. `test/google_fonts_pin_test.dart` holds all of this: it pins both majors, pins that we use no `ShellRoute` (adopting one means re-evaluating 18.0.2's semantics fix rather than skipping past it), and — the gate — reads the live SDK to check it still defines `TextTheme`. When a Flutter upgrade makes that check fail, that is the signal to raise `google_fonts` and delete the guard. Its first version counted three parents up from `Platform.resolvedExecutable` (which is `flutter_tester`, not `dart`, under `flutter test`), found nothing, and returned early — **green and hollow**; it now walks up until it finds the marker and fails outright if it cannot, because an inert guard is worse than a broken one.
- **App Check — sending, not enforcing (yet)**: `main.dart` activates App Check (Play Integrity on Android; App Attest with DeviceCheck fallback on Apple, skipped on web for lack of a reCAPTCHA site key), so clients now *send* attestation tokens. **Nothing verifies them**: there is no `enforceAppCheck` in `functions/index.js` and no enforcement in the Firebase Console — and turning either on today is a **service outage, not a hardening**, because the public release 1.2.46 does not carry the package at all, so every request from every current user would be rejected. The gate is: a version carrying App Check has rolled out and the Console's App Check metrics show verified requests near 100%. Two caveats to settle **before** enforcing: `ios/Runner/AppDelegate.swift` calls `FirebaseApp.configure()`, which makes iOS silently fall back to DeviceCheck instead of App Attest ([flutterfire#18613](https://github.com/firebase/flutterfire/issues/18613)); and the React admin panel has no App Check, so enforcing on Firestore breaks it too. `test/app_check_guard_test.dart` pins both halves — that tokens are sent, and that enforcement is still off; if it fails because someone enabled enforcement, the question is whether the rollout gate was met, not how to silence the test. Procedure in `production_deployment_guide.md`

## Decisions of the third batch (2026-10-05)

- **Riyadh time has one home — `functions/ksa_time.js`.** Cloud Functions run in UTC (no `TZ` is set anywhere; `timeZone: "Asia/Riyadh"` on `onSchedule` governs *when the cron fires*, not the process). So reading local components off an **absolute instant** returns the UTC hour — Riyadh minus three, and "yesterday" before 03:00. The formula (shift +3h, then read `getUTC*`) was hand-written in **seven** places and **two did not shift**: the two server-side order creators, `verifyMoyasarPayment` building an order from payment metadata (the Apple Pay / native-pay path) and `reconcileOrphanPayments` recovering an orphan payment. Both wrote `booking_time_slot` **three hours early**, and that is not cosmetic: `capacity.js` counts a driver busy *from `booking_time_slot`* for `hours_contracted`, so 11:00–15:00 was blocked while the real 14:00–18:00 stayed free — **a double-booked driver**; the driver dashboard announced the wrong hour; the client reminder reads `d.booking_time_slot ||` a *correct* fallback, so the wrong stored field bypassed the right one; the invoice printed it; and `booking_date` slid a whole day for a 00:00–02:59 booking. **It was a regression a fix introduced:** before `parseKsaIso`, the naive string was parsed as UTC so `getHours()` returned the Riyadh wall-clock numbers *right by accident* while `service_date` was stored three hours late. The instant was fixed and the derivative was not — and `parseKsaIso`'s own comment mentions the derivative without touching it. A distinction the guard depends on: reading local components off a date **built from components** (`new Date(y, m-1, d)` then `getFullYear()`) is correct (same zone out as in) and is still done in three places (contract visit generation ×2, the schedule day sweep) — so the guard pins **the source of the two booking fields**, it does not ban `getDate`. And `3 * 60 * 60 * 1000` is not always a zone offset: in `opsHealthSweep` it is a three-hour grace after the visit ends (next to a 12-hour one), so the guard bans it only inside `new Date(` and then asserts the grace is still there, or it would have nothing to distinguish it from.
- **`payWithWallet` was the fourth payment path that did not reopen a system-cancelled order.** `cancelStaleUnpaidOrders` cancels a pending unpaid order after 30 minutes with `cancel_reason='unpaid_expired'`; verify/webhook/reconcile all merge `reopenFieldsIfSystemCancelled` into the `is_paid` flip, and **a comment describing that defence in detail sat in `index.js` above `_parseKsaIso` with none of the code it described**. Wallet payment left the order `cancelled` and `is_paid: true` — money taken, no service, no refund. **Latent, not live, and saying so matters:** no UI path creates an `orders` doc and then pays it by wallet 30+ minutes later (the summary screen mints a fresh id per attempt, and the wallet path writes the doc seconds before the call) — but `payWithWallet` is a public callable accepting any order id the caller owns, so parity is the guard. `refund_engine.test.js` pinned "three sites" and failed on the fourth: reviewed and updated deliberately, not silenced.
- **Coupon *eligibility* lives in `functions/coupons.js`; the amount was never the whole question.** `_computeTrustedDiscount` exists so a client cannot inflate `discount_amount` — and it checked `status` and `expiry` only, omitting the three the client checks in `order_service.validateCoupon`: `target_user_id` (a referral coupon is addressed to one client, its code is **deterministic** — `REF` + six chars of the uid + `10` — and is pushed in plain text, so another client can spend it), `restricted_zones`, and `uses`/`maxUses` — whose "final prevention is part of server pricing" the `countCouponUseOnOrderCreate` comment promised and server pricing did not have. The order is written from the client's device with `coupon_code` and `discount_amount`, so the path is reachable (tampering, not something an ordinary client hits — the distinction is in the comment). **And rejection alone is not enough:** raising "expected" only flags at `ratio < 0.5`, so an ineligible 10% coupon yields `ratio = 0.9` — no mark, no alert, nothing — which is exactly the referral coupon's rate. So reasons are classified: `ESCALATED_PROBLEMS = {other_user, other_zone}` (what an honest client cannot reach) alerts the admin; the rest are marked `coupon_rejected_reason` without an alert, because a race between apply and pay reaches them in good faith. The client is served either way (Tier A marks and alerts **with** service), so no legitimate order is refused.
- **`promo_codes.expiry` existed in two types, and the server understood one.** The Flutter editor writes `Timestamp`; the web panel wrote the raw `<input type="date">` **string**, and the server's check was `typeof c.expiry.toMillis === "function"` — a string has no `toMillis`, so **the whole check was skipped**: every coupon created in the web panel had no server-side expiry. The Dart client checks both types and blocked it, so the UI was stricter than the server. The panel knew about the mismatch **on read** (a comment says the admin app stores a `Timestamp`) and reproduced it on write. The panel is fixed; `couponExpiryMs` reads both types anyway, because string documents exist in production — fixing the writer is not enough. Related: `showDatePicker` returns **midnight**, and `expiry` is compared `< now`, so a card reading "expires 2026-12-31" was dead on the morning of the 31st and "expires today" was dead at creation. Both editors now store the **last instant of the chosen day** (`endOfDayLocal` / `endOfLocalDay`); the fix is in the writers, so existing documents keep their instant.
- **An invoice's issue instant has one source — `lib/utils/invoice_stamp.dart`.** Five of six sites building the ZATCA QR passed `timestamp: DateTime.now()` — the moment the **file** was generated — and `zyiarah_pdf_service` printed "التاريخ / Date" from `DateTime.now()` too. On the happy path the gap is seconds, but the invoice has **two implemented regeneration paths** (`invoice_pdf_status: 'retrying'`): the client's button on the success screen and the admin's in the invoice log. Regenerating an invoice that failed days earlier printed **today's date** on a simplified tax invoice for an order paid days before, and its QR (Tag 3 — the supply date ZATCA reads) carried the same wrong value. In the admin screen the `InvoiceView` loading the row **already held** the right `issuedAt` and `DateTime.now()` was passed next to it. And `InvoiceView.qrData()`'s comment claims it is "the same code printed in the PDF" — so one invoice carried **two different QR codes** and the comment denied it. `invoiceQrFor` is now the single gate to `generateZatcaQrCode` from `lib/`, `generateAndUploadInvoice` requires `issuedAt` and prints it, the two retry paths derive it from the document, and the three immediate-issue sites capture `DateTime.now()` **once** for both the print and the code.
- **Account deletion stranded the wallet balance, and its dialog promised what does not happen.** `processAccountDeletion` deletes the Auth user, `users/{uid}` and the FCM tokens — and **nothing in it looked at `wallets/{uid}`**. The auth identity goes and the balance stays in a document keyed by a uid nobody can ever sign in with again: the client's money held forever, with no notice and no record of the debt anywhere; the profile screen, which *has* the balance loaded for the card that displays it, did not mention it in the confirmation dialog. Now: read the wallet **before** deleting auth (order is the check — a read afterwards prevents nothing), record `wallet_balance_at_deletion` on `account_deletions/{uid}` where humans read it, mark the wallet `owner_deleted`, and alert `super_admin`/`accountant_admin`. **We do not zero the wallet** — zeroing destroys the evidence of the debt — and **deletion still proceeds**, because the right to delete is an Apple requirement and is not withheld over a debt the business owes; the wallet read sits in its own `try` and a failure is logged, never thrown. The dialog said "all your data, **invoices** and past services will be permanently erased" and "right to be forgotten: **all** your tracking records will be deleted" — both untrue: tax invoices and orders are retained under the VAT regulation and `processAccountDeletion` never touches `orders`, which keep `client_name`/`client_phone`/`client_email` as recorded. **The first draft of this fix replaced the lie with another one** ("the rest is anonymised") — nothing in the repository anonymises an order; the guard now bans the word until something justifies it.
- **`lib/utils/qatrat.dart`: the points rate once, and the number shown comes from the deposit.** `50` was hand-written in five places (the server minimum, the server's division, the button's condition, the round-down, the progress bar) — the VAT story's shape, so unification is openly **preventive**. What was not preventive: `redeemQatratPoints` returns `{success, newBalance, newPoints}`, the Dart service returned a `bool` and dropped both, and the screen recomputed the amount itself (`earned = toRedeem / 50.0`) and showed it. So "redeemed 100 points for 2.00 SAR" was a figure that never came from the deposit — and if the rate ever diverged she would be told a number that was not credited. The screen now shows the difference the server actually made, and says success without a figure when the number is absent (an older server), the same shape as "—" elsewhere on the card.
- **An operational broadcast could not be sent from the web panel at all.** `isMarketingBroadcast(data)` is `data.operational !== true`, so **every broadcast is marketing by default** and `_deliverBroadcast` drops everyone who turned off "offers and marketing", push and in-app box alike. The Flutter editor has an explicit switch for this; `Notifications.tsx` **never wrote the field**. A maintenance, outage or schedule-change notice sent from the panel was withheld from every client who opted out — and the panel showed "sent successfully" with an ordinary-looking history row. The panel now carries the same switch with the Flutter editor's wording **verbatim** (the difference in wording is a decision, not taste) and resets it after sending, or "operational" would stick to the next broadcast. The guard pins **the set of writers** of `notifications_log` plus that each one writes the field — and it found a third writer I had not counted (`zyiarah_messaging_service`, the scheduling path), which passes `operational` through from the screen rather than relying on its own default, so it is not a hole.
- **The web panel could not put a product in the companies store.** `products.store_audience` ∈ {`client`, `companies`} and absence is `client` for backward compatibility (`store_service.dart`) — a default meant for **old** documents, not for one created today. `StoreProducts.tsx` wrote `{...formData}` and `formData` had no such field, so every product created there landed in the client store silently and there was no way to reach the companies store; editing a companies product from the panel preserved the field (`updateDoc` only touches what it is given — checked before claiming it) but the admin could not see which store it belonged to or move it. Fixed with the Flutter editor's own picker and a row badge.
- **A driver nobody has rated showed "5.0 ★" — and was ranked as if best.** Both provisioning paths seed `rating: 5.0` on the driver document **with no counter**, and `aggregateDriverRating` excludes that seed from the average explicitly (`count > 0 ? ... : 0`) — so the server itself knows 5.0 is not a rating. Two surfaces displayed it as earned: `admin_staff_performance_screen` defaulted `rating_avg ?? 5.0` and then **sorted** by rating × completed, so a driver with 17 completed and no ratings (85) outranked one with 20 and a real 4.2 average (84) and the "top performer" card could name someone nobody rated — the display was not the only thing wrong, the ranking an admin acts on was; and `Drivers.tsx` printed `{driver.rating}` raw. This is the client-side "تقييمك 4.9 ★" defect on the driver side, with one difference: it becomes real after the first rating, so **the discriminator is `rating_count`, not the presence of `rating`**. Unrated now reads "—" and sorts after the rated by completed count alone. The seed itself is left: documented, server-excluded, and harmless once both surfaces read the counter. A third site looked identical and is **not** a defect: `admin_insights._buildReputationSentinel` reads `rating ?? 5.0` but on **orders**, gated by `rating_comment != null`, so the default cannot pull an unrated order into the low-rating list — left as is, with the guard pinning the comment condition because losing it would make it a real defect.
- **A dead free-order branch that would have produced an order nothing dispatches.** `payment_summary_screen` carried a `'subscription'` payment branch creating a free order (`isFree: true` ⇒ `amount: 0`, `is_paid: false`), and `_selectedPaymentMethod` is **never set to it** (the offered options are card/tamara/stc_pay/wallet; Apple/Google Pay call the handler themselves). Nothing saw it: `no_dead_code_test` covers `lib/services/` and `lib/utils/`, **not the screens** — a gap worth naming. Had it ever been wired it would have been a compound silent defect, because four server paths require payment: `onOrderWritten` gates assignment on the `is_paid` flip (**no driver, ever**), `capacity.countBookings` skips `is_paid !== true` (consumes no capacity, so the day is sold twice), `remindClientsUpcomingAppointments` requires paid-or-assigned (no reminder), and `cancelStaleUnpaidOrders` exempts only Tamara/Tabby and a Moyasar payment id (**cancelled after 30 minutes** as `unpaid_expired`). Real subscription visits never pass through the screen at all: `activateContractOnPaid` generates them server-side with `is_paid: true`, so they are assigned, counted and reminded like any paid order — deleting was right, not wiring. The guard pins the deletion **and its reason** (the four conditions, and that the comment carrying the reason survives), and bans exempting `subscription` from the stale sweep, since that would hide the defect rather than fix it.
- **One pattern keeps recurring, so name it: a decision field read with a silent default, known to only one editor.** Four instances now — the force-update build keys (2026-10-04), `show_in_offers`, `operational`, `store_audience`. Three of them in one batch. The shape is always: a reader defaults a missing field to something plausible, one editor exposes the decision, the other does not write the field at all, and the result is a quiet wrong with a successful-looking UI. So the guards here compare **the whole set of fields each editor writes** (as `amounts.test.js` and `app_update_keys_test` do) rather than asserting one field exists.
- **Two method notes.** (1) A guard that strips comments and then scans for a term **fails on its own documentation** — it happened three more times in this batch (`timestamp: DateTime.now()`, the word «يُجهَّل», `/ 50.0`), so each now strips comment lines *and then asserts the term is still in the raw text*, so over-stripping cannot hollow the check. (2) **Extracting a written field set by matching `'key':` is blind to a key written as a constant** — the first zone-document diff reported a divergence that did not exist, because `admin_hourly_zones_screen` writes `kEventWorkerHourPriceField:`. Resolve `const String kX = 'y';` before comparing. Both the zone document (22 fields each side) and the two package catalogs (`subscription_packages`, `event_worker_packages`) were then confirmed **identical** — those mirrors hold and their comments are accurate.
- **Still open / owner-only.** The server-side fixes (Riyadh time, coupon eligibility and expiry, account deletion) do not take effect until `functions` is deployed, and the panel fixes until the panel is deployed; both deploy automatically on `main` unless the merge message carries the skip marker, in which case run the two workflows by hand. `firestore.rules` was not touched in this batch. `Timestamp.now()` vs `serverTimestamp()` is still mixed in the panel (`cancelled_at`, `completed_at`, `processed_at` come from the admin's browser clock) — noted, not changed, because each is a display/audit field rather than a money comparison.
